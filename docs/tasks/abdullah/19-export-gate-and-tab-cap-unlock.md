# Task: Unlock the data-export gate + dashboard-tab cap, fix the 7 tests it broke

## Why
`src/services/gates/export-resolver.ts` was the last genuinely-active multi-tier billing gate found in this fork — unlike some earlier locks this session found already dead, this one was confirmed LIVE: `curl https://worldmonitor-one-theta.vercel.app/api/product-catalog` shows this deploy actually exposes a purchasable "Pro Business" tier, which is exactly the tier this gate was checking for (`catalogExposesProBusiness`). Per the mission (no Pro feature should ever require payment), it was unlocked. This task covers describing that change accurately and fixing the test fallout.

## What changed — the resolver

`src/services/gates/export-resolver.ts`:
- `resolveExportLock(_input)` — was a 7-step affirmative-denial chain reading `signedIn`/`features.dataExport`/`features.tier`/`billingState`. Now unconditionally `return null` (never locked).
- `resolveAvailableExportFormats(_input)` — was branching on the same fields to return a filtered format list or `[]`. Now unconditionally `return allExportFormats()` (`csv`/`json`/`pdf`, always).
- `resolveTabCap(_input, _currentTabCount)` — was capping signed-out users at `FREE_TAB_CAP` (3) and signed-in users at `features.maxDashboards`. Now unconditionally returns `UNCAPPED` (`{ allowed: true, cap: null, pendingActivation: false }`).
- Removed the now-dead `decideTabCap()` helper and the now-unused `getBillingGateOverride` import; kept `BillingUxState` as a type-only import since `ExportGateInputs.billingState` still needs the type even though nothing branches on it.
- `FREE_TAB_CAP` (still `= 3`, still exported) is UNCHANGED — it's a drift-guard value checked against `convex/config/productCatalog.ts`, not itself a lock.
- All three functions kept their exact original signatures (params prefixed `_` for `noUnusedParameters`) and a comment pointing at this doc — same "keep the choke point, neuter the behavior" pattern tasks 08/13 used for `hasFeature()`/`checkEntitlementDetailed()`, so a real billing backend could slot back in later without touching any caller.

Everything downstream of the resolver — the catalog-activation probe (`catalogExposesProBusiness`, `primeExportGateActivation`, `isExportGateActive`), the reader (`src/services/gates/export.ts`'s `evaluateExportGate`/`evaluateTabCap`/`evaluateAvailableExportFormats`), and every component that consumes a verdict (`ExportGateControl`, `PanelTabBar`, `setupExportPanel`) — is untouched. They still run for real; they just always receive an unlocked/uncapped verdict now.
