# Stale "resilienceScore is locked" test debt (flagged by task 24, cleaned up here)

Task 24 flagged 14 pre-existing failing tests across 5 files, all assuming `LAYER_REGISTRY.resilienceScore.premium === 'locked'` — a state that's been false since task 03 (2026-08-22, de-paywalled). Same class of debt task 14 already cleaned up elsewhere, just never caught in these files.

## Root cause, confirmed before touching anything

`resilienceScore` was the ONE real locked map layer this whole gating system (`isLayerEntitled`, `sanitizeLockedLayers`, `isLayerToggleAllowed`, `isLayerCommandAllowed`, `PremiumLayerGate`, etc.) was written against and tested with. Since task 03 removed its `'locked'` marker, `LAYER_REGISTRY` has had **zero reachable locked map layers** — confirmed permanent by `tests/docs-stats-plan-layer-entitlement.test.mts`'s own already-updated assertions (`REAL_STATS.lockedLayerKeys` is `[]`). The generic gating machinery itself is correct and still fully functional — it was just never re-pointed at anything after its one real fixture went away.

## What was actually broken (5 files)

1. **`tests/docs-stats-plan-layer-entitlement.test.mts`** (1 test) — genuinely live bug, not test debt: `public/pricing.md`'s machine-readable JSON block still shipped `"58 map layers (Resilience is Pro)"` on the real pricing page. Traced to the root cause: `scripts/generate-public-product-facts.mjs:521` hardcodes that string every time `npm run product:facts` regenerates the doc, so a manual pricing.md edit alone would've been overwritten on the next run. Fixed the generator (removed the stale caveat, updated its comment to point at task 03), then hand-applied the same fix to the currently-checked-in `public/pricing.md` to match without running the full regenerator (which touches ~10 other files' real prices — out of scope, no reason to risk that diff for a one-string fix).
2. **`tests/map-layer-executable.test.mts`** (7 tests), **`tests/map-svg-layer-gate.test.mts`** (3 tests), **`tests/map-layer-initial-url-gate.test.mts`** (2 tests) — pure test debt. These test the GENERIC gating machinery, not resilienceScore specifically, so each got a synthetic `zzzTestLockedLayer` patched onto `LAYER_REGISTRY` for the file's duration (`before`/`after`, shaped like resilienceScore's real definition: flat-only, deckGLOnly) instead of asserting something false about production config.
3. **`tests/search-cmdk-premium-layer-gate.test.mts`** (6 of 8 tests) — different case: this file exercises the real `SearchManager.handleCommand` source (parsed and transpiled live from `src/app/search-manager.ts`), which has a `view:resilience` shortcut **hardcoded to the literal `resilienceScore` key** (`search-manager.ts:601`, not a generic lookup). A synthetic key can't stand in for that. Instead, `resilienceScore.premium` is synthetically re-locked for this file's duration only, with a comment explaining why — this is honestly a wiring/integration regression test for issue #6045, not a "verify resilienceScore is locked" test.
4. **`tests/map-layer-executable.test.mts`'s "consumes stale resilience ownership after a free-to-Pro CII sequence"** — a related but distinct case within file 2: `restoreGateOwnedLockedLayers`'s CII/resilience mutual-exclusivity branch (`map-layer-definitions.ts:589`) is also keyed by the literal `'resilienceScore'` name. This scenario is unreachable in production today (resilienceScore can never enter `gateOwned` since it's never locked) — wrapped just this one test in a local try/finally that locks/restores `resilienceScore.premium`, kept as a regression guard in case a future re-lock reintroduces the interaction.
5. **`tests/dom/globe-premium-layer-gate.test.mts`** — false alarm, not actually broken. This is a Vitest file (`vi.mock`, `expect`) that was being run through `tsx --test` (Node's built-in runner), which can't execute Vitest syntax — it "failed" as a single crashed suite with no sub-test detail, which is what made it look like part of the 14. Run correctly (`npx vitest run --config vitest.dom.config.mts`), it was already 4/4 green — its gating functions (`getPremiumLayerPresentation`, `PremiumLayerGate`) take `premium`/`authState` as plain arguments, never touch `LAYER_REGISTRY` directly, so task 03 never affected it.
